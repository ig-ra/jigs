# Ticket loop: from `/igr:ticket start` to `/igr:ticket finish`

The working loop for every regular ticket, in any repo. Terms from `../SKILL.md`: `REPO` (canonical checkout), `BASE` (default branch), `SLUG` (GitHub repo), `LOCAL` (the worktree's ignored `igr/` folder, deleted with the worktree). `LOCAL` holds every ticket file: models, briefs, answers, plan, findings. `/igr:ticket start` comes before this file and `/igr:ticket finish` after it (both in `../SKILL.md`). Save corrections to the loop in this file, written generically: the skill serves any repo and ticket, so rules carry no ticket-, PR- or repo-specific examples, and no names or dates (git records who changed what and when). Repo-specific practice (review bots, merge rules) lives in that repo's project memory.

Run the whole loop without being asked again, from investigation to a merge-ready PR.

**Continuation checkpoint.** Keep `<LOCAL>/resume.md` current using [resume.md](resume.md#save-the-checkpoint) at fixed events: each report stop below, each `tk step` call, each review or check result, and before a handoff or intentional stop. When the human corrects how I work, append one line to `<LOCAL>/corrections.md`. After a restart or compaction, `/igr:ticket resume` validates that checkpoint and continues at its recorded position.

**Session handoffs.** My session resets at three points only, using [resume.md](resume.md#hand-off-to-a-fresh-session): after approval (Before code, step 7), when codex first reports a PR ready (After code, "PR ready"), and when the next PR starts after the previous one merged ("One PR at a time"). The fresh session continues from the checkpoint without repeating intake, design or approval. Trivial changes do not hand off.

**Report only at:**
- the hidden-decisions poll (Before code, step 1);
- the approval point (Before code, step 6);
- the exit (After code, "Exit");
- a disagreement with codex that three rounds did not close;
- a step that needs a human decision, including a review bot repeating an answered point.

Nothing in between unless I am blocked or something is irreversible. Reports follow `~/.claude/memory/talking-to-igor.md`: verdict first, and name the rows and points, never number them.

**Never call a review clean**, or relay "no findings", until `<LOCAL>/review-claude.md` has all three tables of After code step 1 filled. If I checked only part, say which part.

**Round trips are the cost.** Each brief → wait → re-read cycle costs 15-20 minutes of wall clock. Merge rounds that do not need to be separate; never drop an independent pass or a reviewer to do it.

**The band.** Both `tk step` and `hooks/ticket-band.tsx` use `<worktree>/igr/state.json`, in `LOCAL`. The hook prefers that file; while existing sessions finish, it reads the old temp path only when the new file is unavailable. New `tk` writes use only the worktree path.

Use `<skill base directory>/scripts/tk step <KEY> <line> <status>` at every state change. The absolute script path passes the guard. Lines: `implement`, `reviews`, `checks`; statuses: `running` ⏳, `fixing` 🔧, `done` ✅, `todo` ⬜, `fail` ❌. `tk` locks and atomically updates the ignored file, preserves unrelated fields, and stores timer ids in `tk.estimates`. Use `--ticket-url <Linear URL>` for the ticket link and `--pr <number>` for PR number/URL; no hand edits.

- **`implement`** (Implement → rebase on main → open PR): `running` from dispatch; `done` when the PR is open and rebased on latest `BASE`: `<skill base directory>/scripts/tk --cwd <worktree> step <KEY> implement done --pr <PR>`.
- **`reviews`** (simplify + codex + claude → fix → rebase + re-push): `running` during reviews; `fixing` during pooled fixes; `done` after rebase/push and my review of the final diff.
- **`checks`** (Architect + CI): `running` while waiting; `fixing` during CI/bot fixes; `done` when CI is green and the architect bot approves with every thread answered.

Never add lines or Before-code steps. A new push resets each invalidated line with `tk step ... running`. For the next PR, use separate commands for `implement running`, `reviews todo`, `checks todo`, clearing old notes with `--note ""`; `--pr` overwrites the PR metadata when it opens. `tk` does not reset other lines automatically. Finish sets all lines to `done` with the merge sha as the checks note before removing the worktree and its files. On exit 3, manually update only the intended fields in the ignored worktree file, preserving timer ids.

## Before code

**Two independent passes, then talk.** Codex judges every problem without seeing my solution, and I judge it without seeing codex's. Comparison starts only when both solutions exist; then we decide together what to keep, do and change. This holds for the ticket design, for new work in the middle of a PR, and for review findings.

**Trivial changes: I do them myself.** A change is trivial when step 1 leaves nothing to design and nothing for codex to check: the edit follows directly from the ticket and the code, it is small, it has one sensible shape, and it hides no decision. For a trivial change I skip codex entirely (steps 2-5 and 7). I write Model A and post it as the living comment, where it is the contract (B = A). Then I make the edit, run the gates in "Rules for both halves", commit, push and open the PR myself. After code still runs in full (the three reviews, CI, the bots), and I make its fixes myself too. If I am unsure whether a change is trivial, it is not.

1. **Investigate, then the hidden decisions.** I read the code on the latest `BASE` and measure prod populations read-only. A rule that depends on data that changes over time (membership, state transitions) gets a prod measurement of that change first.
   The investigation ends with **the decisions this ticket hides**: behaviour, semantics, scope and limits that only a human can answer, and only those that would change a Mental Model row. I ask them as one poll and record the answers before codex's first pass. Each option is the smallest form of that choice; anything extra (a counter, a log, a flag, a test) is its own choice. A code ticket that hides a product decision otherwise reopens its approved contract once per decision.
   Before the plan, read the related, blocking and sibling tickets, including other teams' tickets that touch the same module, and our own earlier comments on them. A contract we already asked another team for is a decision: reversing it goes to the human with that comment quoted. Before calling code unused, read its owner's latest comments; absence of callers is not absence of plans.
2. **Codex's independent pass, in parallel with mine.** I spawn codex (`codex-<N>`, right split, on the ticket worktree; read `driving-codex.md` and `herdr-codex.md`, next to this file, now) and brief it first. The brief gives the problem, never my solution:
   - the ticket goal and acceptance criteria, and the recorded answers;
   - the bigger goal, the project's end state, and what is scheduled for deletion;
   - facts codex cannot see (prod numbers, other repos);
   - the standing rules: KISS, no defensive code, no flags, delete orphans;
   - **smallest design first:** propose the smallest change that meets the goal; heavier designs (new tables, transactions, API fields, workflows) appear only as options with their cost;
   - write your own view and Mental Model to `<LOCAL>/codex-design.md` **before** opening `<LOCAL>/model-A.md`; if that file exists by then, compare in the same turn, otherwise stop after writing your view;
   - size the work in rounds per step (change → check → read → decide), never hours.

   While codex works, I write my suggested implementation and Mental Model A to `<LOCAL>/model-A.md`. A is never edited afterwards: it is the drift baseline. Nothing goes on the ticket yet, because codex reads ticket comments. Mental Models use the shape in `mental-model-contract.md`, next to this file: Ships, then ADD / CHANGE / REMOVE rows, then Unchanged, in 50 lines or fewer.
3. **One compare round.** If codex stopped before A existed, I send A now. The compare brief carries everything at once, per driving-codex "Partner, not push": what to keep, drop and change, with reasons; "if the two designs match, say so in one line and do not manufacture a difference"; "name what you would cut for the smallest change that still moves the goal; then say ready, or name the one gap". Every agreed change is a Mental Model row. Only a real disagreement opens another round; three rounds without converging goes back to the human as the disagreement itself.
   Method: codex works from its own plan, with no Superpowers workflows and no internal review loops (reviewing is the After-code job). **Every implementing run of more than one commit**: codex writes `<LOCAL>/plan-<N>.md` before code, one checkbox step per commit with files, done-criteria, the gate commands, an expected size, and the effort codex judges the step needs (`medium` or `high`) with a few words of reason, every later correction merged into it.
4. **Drift and overengineering check.** Model B is the agreed row set when codex says ready. Before the approval report, I go through every B row, tests included, not only those that differ from A, and ask two things: does the ticket's goal need it, and is what it guards broken by this change, or is it a gap that already exists? A row both models share, or one copied from the ticket text, gets the same check: agreement is not evidence, and ticket text counts as a human decision only when a recorded answer says so. For a test, also ask: what real failure would it catch that nothing else catches? Open the existing tests first; a row that reshapes an existing test adds nothing new. If none, cut it. For every row I also name the simplest alternative, including a different shape of the deliverable that would make the row unnecessary, and the reason I rejected it, marked measured or guessed. A guessed reason does not count: I measure it, or I take the simpler alternative. A row that fails either test goes to Follow-ups; a row that moved us off the goal goes back to codex until it is justified or reverts. Cuts go to codex as one brief ("agree, disagree, or better?"), and `<LOCAL>/A-to-B.md` records each cut with its reason. If the answer to a cut brief adds any part, even inside an agreement, that part gets the same check before B is written. A cut round that adds is not the last round.

   **Then a KISS pass over the whole design.** Once B is settled, read everything that will ship (A's parts and codex's together) as one piece, like a reviewer seeing it for the first time. For each part (each field, counter, log, doc line, test change), ask: does the goal still hold without it? What does it cost in places touched, against how often its path runs in prod? Details I put into a poll option are mine, not the human's choice. Write one line per part, keep or cut, to `<LOCAL>/kiss-pass.md`. Cuts that change a recorded answer go to the human; the rest go to codex as one brief. The approval report waits for this file.
5. **Estimate.** Count the rounds, run `python3 <skill base directory>/../agent-estimate/estimate.py est codex <low-high>`, and report the script's minutes (codex's own number only if it differs, never human days).
6. **Approval.** I report in plain words, with no file paths, no "where" column and no numbered lists, in three short blocks:
   - **Model A**, grouped as bullets: **Remove**, **Add**, **Change**, **Tests**, **Unchanged**. Each item fits in one line; sub-bullets appear only under a group with several items. Skip an empty group.
   - **B, the differences from A**: derived by comparing A and B row by row, test rows included, never written from memory. One line each, marked `+` (added), `−` (dropped) or `~` (changed), with its reason in a few words. Do not repeat what B shares with A. A row whose scope grew counts as `~`.
   - **Simpler options rejected** (from step 4): one line per B row that has one: the simpler option, why it was rejected, and `(measured)`. A `(guessed)` reason never reaches this block.

   **Why:** a cut check I tick myself passes even when I rejected the simpler option on an unmeasured risk; printing the reason and its evidence in the report is what lets the human catch it before code exists.

   Then the estimate in minutes, then the one thing to approve. The full B table (with tech and paths) goes on the ticket's living comment and in `<LOCAL>/model-B.md`; the A-to-B reasons go in `<LOCAL>/A-to-B.md`, not on the ticket. Once approved, B is the contract, and I post the living "Suggested implementation" comment on the ticket: the full suggestion, ending with Model B. Each later approved change updates that comment so it always matches what the PR ships.
   For a **decide** ticket the loop ends here: I record the decision in the ticket's Answer and living comment, open or update the implementation tickets, and run `/igr:ticket finish`.
7. **Fresh sessions, then implement.** First hand myself off with phase `develop` ([resume.md](resume.md#hand-off-to-a-fresh-session)); the fresh session starts at the codex `/clear` below and does not hand off again. Send `/clear` to codex. Its first prompt points only to the written contract (ticket, acceptance criteria, living comment, plan file for big work) and the stop conditions: "everything there is decided; do not reopen it; if something is missing, ask". Its first answer is a short read-back (scope, steps, out of scope) before any code; a gap means the contract is incomplete, so fix the contract, not the chat. Then codex implements, commits, pushes and opens the PR (Conventional Commit title with the ticket key) without waiting for my review.
   Briefs ask for short tool output: `rg -l`, `sed -n` ranges, `| tail`. Never print whole large files or full test logs into the session.
   **Status:** the first push of the ticket's branch to GitHub, by codex or by me, moves the ticket to In Review (`save_issue(KEY, state: "In Review")`) as soon as I see it (watcher fire or codex's report). `/igr:ticket start` already set In Progress.
   On implementing dispatch: `<skill base directory>/scripts/tk step <KEY> implement running --dispatch --agent codex --rounds <low-high> --task "<short>" --model <model>`. Fix dispatches use the affected line (`reviews fixing` or `checks fixing`). `tk` starts the estimate and stores its id under that line in `state.json` → `tk.estimates`; one open id per line. One timer per implementing dispatch; question rounds are not logged. For exit 3, check whether the timer already started before manually using `estimate.py start`; retain its id in the working notes and close it with `estimate.py done` on report.

## After code

**Codex owns every edit**, except on a trivial change (Before code, "Trivial changes"), where I own every edit. Otherwise I do not patch the branch unless told to make a specific edit myself.

**One PR at a time.** "After code" runs per PR. When a ticket ships several PRs, codex stays on the open PR through review, fixes, CI and the review bots until it merges; the next PR starts only after that. Exception: once the open PR is green and in the merge queue, a next PR that touches unrelated files starts at once, with a fresh codex on its own worktree cut from the latest default branch; do not ask. When the next PR starts after the previous one merged, hand off first with phase `develop` for it.

**PR ready.** When codex first reports a PR ready (checkpoint phase `develop`), record in the checkpoint the PR number, the observed head and base SHAs, the checks it ran and its deviations from the contract, then hand off with phase `review`. The fresh session starts at step 1 from the ticket, the contract, the actual diff and the recorded evidence. A fix report while the phase is already `review` keeps the session.

1. **Three independent reviews, in parallel, once per PR:**
   - an Opus subagent runs `/simplify`, report-only (medium effort for an additive change off production paths, high for a production path, never xhigh);
   - the Codex plugin's native reviewer (the same built-in reviewer as codex's `/review`), run from my session as a background shell command in the PR's clean worktree: `node ~/.claude/plugins/marketplaces/openai-codex/plugins/codex/scripts/codex-companion.mjs review --wait --base <base>`, stdout to `<LOCAL>/review-<PR>.md`. Always pass `--base`: without it the plugin reviews uncommitted changes when the tree is dirty, and otherwise diffs against the local default branch, which can be stale. `<base>` is `origin/<default branch>`, or the parent PR's tip for a stacked PR. It is a fresh codex process, so it reads as a reviewer, and the implementing codex keeps its context. It takes no custom text and does not know the contract, so findings that match an accepted trade-off are dropped at verification (step 2). For a design challenge, `adversarial-review` (same script, same `--base`) also takes focus text;
   - **Time my pass:** immediately before each pass (including a rerun), run `<skill base directory>/scripts/tk --cwd <worktree> step <KEY> reviews running --dispatch --review --agent claude --task "After-code review" --model <model>` (add `--pr <PR>` if the band has no PR yet). Keep its fresh id under `tk.estimates.claude-review`, independently of Codex's fix timer. This times my review; the parallel simplify/native Codex reviewers are outside it.

     As soon as my pass ends, run `<skill base directory>/scripts/tk --cwd <worktree> step <KEY> reviews <current status> --report --review --wait-minutes <human wait>`; use `--actual-minutes <duration>` for a late report. Close incomplete or interrupted passes too, with the reason in `--note`.

     For exit 3, follow the [manual fallback rule](../SKILL.md#which-repo): inspect state and the log before a direct `estimate.py start claude --review --task "PR #<PR>: After-code review" --ticket <KEY> --model <model>` or `estimate.py done <id>`; retain/reconcile the review id separately from implementing ids.

   - **My review: gaps, drift, overengineering.** I read every hunk of the diff, tests included, for every commit since the base, and write `<LOCAL>/review-claude.md` with three tables. An empty cell means the review is not done:
     - **Model B → diff:** each B row → the hunk that implements it; each hunk → its row. A hunk with no row is drift or overengineering; a row with no hunk is a gap.
     - **Ticket → diff:** each acceptance criterion and each "What will change" item → the test or hunk that proves it, or "uncovered".
     - **Deleted or changed tests:** each one → every behaviour its assertions proved → where that behaviour is still tested, or "lost" with a prod measurement of whether the state occurs. A test removed as "only about X" often also covers a guard that stays.
2. **Findings: sort, two passes where judgment is involved, one push.** Every finding (the three reviews, bots, CI, a human) goes into one of two tracks:
   - **Judgment track:** the finding would change behaviour, design, a migration, shared infrastructure, locking or the contract, or either of us would reject it. It gets the two independent passes from "Before code". One brief gives codex the findings as written (log lines, bot text, where to measure), with no verdict, fix shape or numbers of mine; codex writes its analysis and proposed fix per finding to `<LOCAL>/findings-<round>.md`, no code yet. Meanwhile I write my own verdict to `<LOCAL>/findings-<round>-claude.md`, using driving-codex "Before accepting a finding" (can the state occur, which regime did I measure, what actually happens). Then one compare round: "agree, disagree, or better?" per finding. Codex fixes and pushes only after we agree; a contract change goes to the human first.
   - **Fast track:** the fix follows directly from the finding and hides no decision (wording, a rename, an orphan, a hardcoded name, a missed test update). One brief, each as "agree? fix and push; if not, stop and write why".
   - **Escalation:** if either side disagrees on a fast-track item, it moves to the judgment track.

   One push per batch carries every agreed fix, with "rebase on the latest `BASE` before the push". A later rebase happens only on a conflict or a merge-queue rejection.

   **Why:** a finding I judged alone and handed over with my verdict got fixed in my shape or rubber-stamped. Codex's independent check corrected a history claim I was about to post on a bot thread, and a gap I had cut on an unverified claim came back from a bot with production numbers.
3. **Per commit:** the diff against its plan step and done-criteria, source, tests mapped to acceptance criteria, docs, and hosted CI on that head. I inspect CI with `<skill base directory>/scripts/tk --cwd <worktree> pr state <PR>`; for failed required checks, `<skill base directory>/scripts/tk --cwd <worktree> pr fail <PR>` gives bounded error lines from completed runs (inspect full logs when needed). Findings go back as questions; once agreed, codex fixes. The implementing codex still never polls CI.
4. **Review bots.** When the repo has a review bot, follow its project memory. Check every review thread at every push with `<skill base directory>/scripts/tk --cwd <worktree> --json pr threads <PR>`, without waiting for anyone to point at them. A thread another bot resolved after the fix still gets my reply with the fixing commit; resolved without a reply is not answered. List all threads, not only unresolved ones (`tk pr threads` shows only unresolved). Exit 8 means unresolved threads were listed (normal). JSON includes all unresolved threads with first/latest comments; read intervening comments via GraphQL when needed. Human and resolved threads remain available through GraphQL for finish/follow-ups. A reply that needs no code change (evidence, or a point the contract already decided) I verify and post myself while codex works; I do not hold it for codex's round. Sort each bot finding into step 2's tracks: a judgment-track finding gets the two independent passes before any fix, or any reply that rejects it. After agreement and the push, reply with the fixing commit or the evidence using `<skill base directory>/scripts/tk --cwd <worktree> pr reply <thread id> <absolute reply body file> --resolve`. Omit `--resolve` when the point must remain open. Judgment and evidence stay mine.

   **Manual fallback on `tk` exit 3** (use request JSON files in `LOCAL`, the manual gh prefix in `../SKILL.md`, and read back before retrying):

   - Reply: `gh api graphql --input <reply request file>` with `addPullRequestReviewThreadReply`; confirm the returned URL has the intended thread/body.
   - Resolve: `gh api graphql --input <resolve request file>` with `resolveReviewThread`; confirm `isResolved: true` and absence from `tk pr threads`. If a reply URL printed before a resolve error, inspect it and retry only the missing resolution.

**When the reviews rerun.** Step 1 runs once, after the first implementation of a PR. At the end, when findings are fixed and the bots agree, I decide whether the diff since the first review is substantial; only if it is, step 1 runs once more on the full PR diff against the base.

**Exit.** The loop ends when CI is green on the PR head, every bot thread is answered with evidence and resolved, and nothing is waiting on codex. When an implementing run's report arrives, close its timer with `<skill base directory>/scripts/tk step <KEY> <dispatch line> <current status> --report --wait-minutes <minutes waiting on a human> --note "<why it differed, if by more than half>"`; select status from actual progress, since the run ending does not itself prove review/CI done. On `--report`, `--note` goes only to the estimate log; it leaves the band note unchanged. For exit 3, inspect the estimate row before manually closing it with `estimate.py done <id> --wait <minutes> --note "<reason>"`; reconcile the failed step's state before resuming. Then I refresh the "Model B → diff" table of `<LOCAL>/review-claude.md` on the final diff and report once: the PR is ready for approval, plus any drift from contract B that table shows. Do not rewrite the contract to match the code.

**CI and merge waits.** In my session, use `<skill base directory>/scripts/tk --cwd <worktree> pr watch <PR> --until checks` (or `threads`, `queue`, `merged`), in the background when needed. Timeouts/intervals are seconds; 124 is a timeout, 8 pending, 1 failed/stopped, 3 API/setup error. `state`/`watch --until checks` proves required checks only; review approval and bot evidence still need inspection. `threads` is independent: merged does not mean resolved. On exit 3, inspect `gh pr checks` and GraphQL `reviewThreads`, review decision and merge queue on the current head manually, using the env prefix in `../SKILL.md`; preserve pending/error distinctions.

For a repo that uses a merge queue, once its approval rules and the loop's exit criteria hold, use `<skill base directory>/scripts/tk --cwd <worktree> pr enqueue <PR>` and confirm queue state with `pr state`/`pr watch --until queue`. **Manual fallback on `tk` exit 3:** `gh api graphql --input <enqueue request file>` with `enqueuePullRequest` and the observed `expectedHeadOid`; read back a queue entry not `UNMERGEABLE`, or the merged PR, before retrying. Follow project memory for repos without a merge queue. Queue admission is not merge proof: `pr watch --until merged` confirms merging, and `tk close` later proves safe local cleanup.

## Rules for both halves

**Hold the bigger goal in every round.** Codex reasons from the code in front of it; its comments pull toward extra guards, compatibility paths and tests for states that cannot occur. Before accepting any addition, ask whether it serves the ticket's goal and the project's end state, and whether it is the simplest shape that does. The goal also adds scope: when the project replaces a system, legacy code and tests the change makes dead go in the same change.

**Every addition earns its place.** Any part added to a design or a fix after the first independent model gets three answers, with evidence, before it enters the contract: (1) can the state it handles occur, and how often (measured, not reasoned); (2) does something that already exists handle it: a helper's documented contract, an existing retry or failure path, a later ticket; (3) what actually happens if it is left out. Cut it unless (3) is real harm that (2) does not already cover. Every round that adds parts ends with the cut question, not only the first. When a brief asks for rigor somewhere, rigor means the cheapest proof that already exists: an existing test, an existing contract, or a one-time run of the real thing. Never new mechanism, and never new test machinery unless it names a real failure that nothing else catches. When the human adds new scope mid-design, I write my own smallest version before codex sees it.

**Why:** every addition can be right on its own terms and the design still grows past the problem; an approval report built from the rows' own justifications never shows that.

**Drift check.** Before approval (Before code, step 6), before the implement dispatch (step 7), before each push or rebase, and before "ready to merge": `git fetch`, then `git log --oneline <BASE at the previous checkpoint>..<BASE> -- <paths in scope>`, and re-read the ticket's comments since the last check. A new commit means: read its diff and PR before going on. A finding that changes a Mental Model row goes to the human before the next step.

**Gates.** Before each commit, once per commit (not after each edit), codex runs only the focused unit tests for what it changed and the build. Database and integration test files run locally only when hosted CI does not run them, or to diagnose a CI failure. Never locally: the full unit suite, the full database or integration suite, golden or snapshot runs, "affected" sweeps, or a combined pre-PR gate. Hosted CI runs everything. No test run may hang forever: use `--test-timeout` if the repo's test command accepts it, else a shell `timeout`. Don't edit tests just to add timeouts. Log long runs to a file; read its tail. A gate counts as passed only with its own output line quoted. Every brief I send repeats this gate list. The focused gate can be waived for a PR: then codex commits and pushes without running anything, the brief quotes the waiver, and hosted CI is the only gate. Treat that as approval to implement at once; the agreed model still goes on the ticket first.

**CI.** Within a plan, codex goes straight on to the next step after a push and ends its turn at the end of the batch; it never polls CI. I watch hosted CI and the bots on every head the watcher reports, and bring a red result as a mid-round steer or the next prompt. Hosted red means the PR is not done.

**Plan-of-record runs.**
- Codex ticks a step in the plan file when its commit lands and logs mid-work decisions there.
- A correction, steer, stop instruction or priority change goes into the plan file as a step or constraint, not only into chat: a compaction can drop a chat-only instruction.
- **Pending a human decision.** Open questions taken to a human are listed in the plan file (or at the end of the living comment when there is no plan file). Codex never classifies them itself until the decision is recorded.
- **Clear between steps:** after each step's commit, codex ticks the step in the plan file. I send `/clear`, then set the next step's effort to the higher of codex's choice and mine (I judge the step from its files and done-criteria before reading codex's choice), then send "Read `<plan file>` and the ticket's living comment, continue from the first unchecked step." Same codex, empty context, so each step starts small. **Why:** a 350-415K-token context made every codex reply take 14-26 s and forced 4-minute compactions mid-step.
- **Compaction** stays the fallback inside a long step: codex compacts itself. The plan file's first line is "After any compaction, re-read this file and the ticket's living comment, then continue from the first unchecked step." When codex's context jumps back up, I send that same prompt once.
- **Late plan:** if a big run has no plan file and codex's context drops below about 30%, I ask for it at the next stop point, before any more code.
- **Scope fence.** Every plan file has a "Not in scope → Follow-ups" section and this Global Constraint: "a finding outside the contract, from any reviewer or test, goes to Follow-ups, never into code". When the feature is off in prod, the plan also says "no new features or hardening". Codex brings the Follow-ups list at each step commit; they become tickets only after approval.
- **Time.** A step with no commit after 1.5 times its expected time, or an uncommitted diff past about twice its expected size, means I check the diff against the plan step; growth beyond the contract pauses codex and goes to a human with its cause. At 1.5 times the ticket's high estimate, I re-estimate from the remaining steps and report it in one line.
- **Watcher.** For every implementing run, keep `<skill base directory>/scripts/watch-codex.sh <codex-name> <worktree> <max-diff-lines>` running in the background. It exits with one line when codex compacts, commits, stops or its uncommitted source diff passes the threshold. On each exit: act (re-read prompt, step check, report or pause), then re-arm it.

**Why rounds and the script:** agent hour estimates are human-calibrated and run several times too high; logged actuals are not.

**New work goes back to "Before code".** A new feature or behaviour change during "After code", even one already decided, waits until the current batch is pushed. Then it goes through Before code steps 2-6 with the same two independent passes: I write my view, codex writes its own before reading mine, we compare and agree (new Mental Model rows), approval is needed if the contract changed beyond that decision, codex implements. The new commit gets the per-commit check and the bots. A behaviour change always counts as substantial, whatever its size, so step 1 reruns once on the full PR diff before merge.

See also "Steer only what changes the current batch" in `driving-codex.md`.

**Why:** the goal is a simple plan that moves the bigger goal, not a plan that only survived review, and every outside finding checked by both codex and me before anything changes.
